# Research Prompt: E-graphs / Z3 for CMake Equivalence Checking

I'm exploring two PL/verification techniques — **e-graphs** and **SMT/Z3** — for
a specific problem: semantic equivalence checking of CMake programs generated by
the **yelu** typed configuration language. I want a realistic assessment of how
practical each approach is, and whether there's a natural fit or fundamental
mismatch with CMake's semantics.

**Context**: cmake's configure-time language is a restricted imperative language
(straight-line code + boolean conditionals, string-typed mutable state, 6
independent namespaces, finite iteration, a few opaque side-effectful commands).
The key PL vocabulary — `src`, `input`, `env`, `build_spec`, `artifact`, and the
actions `eval`, `compile`, `inspect`, `run` — is defined in
`doc/cmake_comparison.md`, which also covers the equivalence levels (`src`,
`interp`, `run`) and the test harness that operationalizes them. Read that first.

The research gap: the test harness proves equivalence at one concrete input `i`.
With n boolean option variables there are 2^n configurations; no test-based level
can prove equivalence for all of them. Symbolic methods are the only path to
closing that gap.

### Scale of the cmake surface (benchmark context)

cmake 4.3 dev (`yelu/vendor/cmake`):
- 133 commands in `Help/command/`
- 431 target properties, 802 variables, 270 modules
- ~431 test subdirectories in `Tests/RunCMake/` (one per command area)

Good benchmark sources for an initial symbolic encoding:
- `Tests/CMakeOnly/` — script-only tests, no compiler needed; pure `eval` programs
- `Tests/CMakeCommands/` — per-command configure tests; exercises `compile`

## Research questions

### Question 1: E-graphs for cmake equivalence

E-graphs (egg / egglog) are typically used for term rewriting and equality
saturation over functional expressions. CMake is stateful and order-sensitive. But:

- The pure fragment (`if`/`else` as `ite`, variable reads as pure lookups in a
  snapshot) might be encodable as terms.
- Could e-graphs model "equivalent cmake statement sequences" — e.g.,
  `set(A foo)` then `set(B bar)` ≡ `set(B bar)` then `set(A foo)` when A ≠ B?

Is there a natural encoding of imperative state transformers into e-graphs that
lets equality saturation prove these equivalences? Or does statefulness
fundamentally break the approach?

### Question 2: Z3 for cmake equivalence

Encode cmake semantics as a symbolic interpreter and use Z3 to prove equivalence:

- Option variables become Z3 boolean constants (free variables).
- `if(USE_MYMATH)` becomes `ite(use_mymath, then_env, else_env)`.
- Variable state is a symbolic map (string → Z3 expr).
- Assert the two final environments differ (∃ assignment where env1 ≠ env2),
  check SAT. UNSAT = equivalent for all inputs.

Anticipated problems:
- Impure commands (`find_package`, `execute_process`) need stubs or exclusion.
- CMake string operations (regex, list manipulation) are complex to encode.
- `env` is a map from string keys to string values — Z3 string sequences might
  handle this but could be slow.

Is Z3's theory of strings (sequences) practical here? What are the known pitfalls?

### Question 3: Comparative assessment

Given the problem structure — decidable fragment, finite boolean inputs,
string-valued state, mostly pure configure-time code, a few opaque side-effectful
commands — which approach is more practical? Is there prior work on:

- Semantic equivalence of Makefile / build-system configurations?
- Symbolic execution of CMake or similar configuration DSLs?
- E-graphs for imperative program equivalence (beyond expression-level rewriting)?

Other approaches also in scope: abstract interpretation, bisimulation, translation
validation.
