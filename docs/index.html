Yelu — a compositional
language for the AI era

A programmable configuration shell language with a typed surface syntax. Separates control (binding, branching, iteration) from theories (domain operations with type checking). cmake is the first target; the architecture generalizes.

Concrete syntax

Yelu's surface syntax is an OCaml-Python hybrid: expression-oriented with ML-style bindings and a Python-ish concrete feel. The parser is implemented and tested (168 parser tests), covering all 14 cmake theories.

Tutorial Step 1

( cmake_minimum_required "3.20";
  project "Tutorial" ~version:"1.0" ~languages:[CXX];

  set CMAKE_CXX_STANDARD "11";
  set CMAKE_CXX_STANDARD_REQUIRED ON;

  configure_file "TutorialConfig.h.in" "TutorialConfig.h";

  let tut : target = Target Tutorial in
  add_exe tut { tutorial.cxx };
  include_dirs tut { "${PROJECT_BINARY_DIR}" }
)

Tutorial Step 2 — with a library

( cmake_minimum_required "3.20";
  project "Tutorial" ~version:"1.0" ~languages:[CXX];

  let math : target = Target MathFunctions in
  add_lib math { mysqrt.cxx };

  let tut : target = Target Tutorial in
  add_exe tut { tutorial.cxx };
  link_lib tut { math };
  include_dirs tut {
    "${PROJECT_BINARY_DIR}";
    "${PROJECT_SOURCE_DIR}/MathFunctions"
  }
)

What is yelu?

Yelu is a research vehicle for language design in the AI era, organized in five layers. Each layer answers a question and builds on the one below it.

Layer 1 — The specimen: cmake

Configuration languages carry disproportionate operational risk — a typo in a variable name, a misordered command, and the fault surfaces three calls later as an empty string. cmake is the exemplar: three decades of accumulated layers (scripting → modules → generator expressions → presets → policy stack) with no cleanup between them. It is widely adopted (important enough that results transfer) yet maximally hostile to automated reasoning (a stress test for the claims).

Layer 2 — The architecture: control side + theories

The language separates a universal control side (binding, branching, iteration, macros) from target-specific theories (per-domain typed constructors and checkers). Theories compose over a shared substrate; the control side is reused across all target packs (cmake, future json, nix).

Checking decomposes into distinct passes — typecheck, wellform, effect, lower, configure — each catching a different class of error without a monolithic type checker.

Layer 3 — The thesis: low entropy

Languages with low syntactic and semantic entropy plus strong local verification produce better model-driven generation and repair.

The target workflow is human-plus-model production with verifier feedback: a model generates or repairs under verifier guidance, a human reviews and directs. The language is optimized for this loop — not for unadorned model consumption, and not for unadorned human authoring.

Layer 4 — pl à la carte

The control side and theory side are independently variable — composable ingredients that can be mixed and matched. This is pl à la carte: not one language, but a design space for assembling languages from parts.

The control side is a set of choices: expression-oriented vs. imperative, stateful vs. stateless, macros vs. functions, gradual vs. mandatory typing. The theory side is domain-specific and self-contained. Any theory pairs with any control side.

For LLM-based evaluation, the control side itself becomes an experimental variable: does a model generate better cmake with an imperative surface or a functional one? With macros or without? pl à la carte makes these questions answerable by experiment rather than by debate.

Layer 5 — The AI-era argument: why now

AI has crossed a critical threshold: models can generate and repair cmake, bash, YAML, Dockerfile — the existing irregular configuration languages. This has two consequences.

First, compatibility with existing syntax is not a constraint. We don't need to retain cmake script syntax for human familiarity — LLMs can translate, a CLI can round-trip, and developers can learn yelu alongside cmake. The locked-in syntax that accumulated over decades can be replaced.

Second, AI is not just a consumer of the language but part of its design motivation. Each theory is a unit of AI tooling: a training unit (fine-tune on per-theory test suites), a prompt context (few-shot examples scoped to one theory), and a tool boundary (each checker is a verifier an agent can call). An agent facing a novel build task doesn't need to know "cmake" — it needs the target theory, the find theory, the install theory, and the control side teaches it how to compose them.

Falsifiability

The thesis makes specific, testable claims:

  1. LLMs using yelu produce fewer type errors, fewer silent semantic errors, and require fewer repair rounds than LLMs given cmake directly, on matched tasks.
  2. Error classes caught by yelu's checker are a strict subset of cmake's own errors.
  3. Adding a new theory requires no modifications to existing theories' checkers.
  4. A second target pack does not require redesigning LANG_TYPES or checking_stage.

What yelu is not

  • Not a cmake replacement. Yelu targets cmake as output; cmake is the specimen, not the thesis.
  • Not a build system. Yelu has no runtime, no scheduler, no dependency graph. It emits text that build systems consume.
  • Not a product. Yelu is a research vehicle for language design in the AI era. The artifacts exist to test the thesis, not to ship to users.
  • Not AI-only. Yelu is optimized for human-plus-model production with verifier feedback — not for either alone.
