Architecture

How yelu-cmake is shaped: two languages, one pipeline, verifier-driven

This page distills the design of the yelu-cmake implementation for someone curious about how the compiler is shaped. For internal contributor docs see doc/yelu_cmake/structure.md and doc/yelu_cmake/design.md in the repo.

Two paired languages

The project hosts two distinct cmake-domain languages over a shared IR. Neither is "more abstract" than the other — they're different decompositions of the same problem.

yelu_cmake

The CMake-command-faithful compatibility form. Stable, closest to emission. What step files build, what the parser produces, what emits to text. The workhorse.

One constructor per cmake command family (ECmakeAddExecutable, ECmakeTargetIncludeDirectories, ECmakeStringConcat, …).

yelu_cmake_normal

The normalized form. Same domain, different decomposition: each theory carries its own value-oriented ctors (EStringConcat, EListAppend, …) without cmake's output-variable shape.

Used for refactoring passes and as the basis for richer typing decisions (Y17). Not on the production emit path.

Translation lives in Yelu_cmake_convert with two near-inverse functions: 

Yelu_cmake_convert.to_normal   : yelu_cmake.expr -> yelu_cmake_normal.expr
Yelu_cmake_convert.from_normal : yelu_cmake_normal.expr -> yelu_cmake.expr

The round-trip property — from_normal · to_normal preserves observable cmake emission — is exercised by 65 lift/lower tests.

Naming aside. The two names — yelu_cmake and yelu_cmake_normal — are intentionally representation-suffix-free. There is no _ir, no _surface, no _string. The bare name belongs to the workhorse; variants get an honest descriptive suffix.

Compilation pipeline

Production cmake-text generation runs entirely through the new typed surface. Two input forms, one converged pipeline: 

From OCaml step files:
  Step file (.ml)
    → Yelu_cmake_utils.{yc_set, add_exe, ...}
    → yelu_cmake.expr
    → Yelu_cmake_emit.emit_ast
    → Lang_cmake.exp
    → Lang_cmake_pp.pp
    → CMakeLists.txt

From .ye concrete source:
  source.ye
    → Yelu_lexer
    → Yelu_parse
    → yelu_cmake.expr
    → (same backend as above)

Two important properties:

  • No bridge on the binary path. The legacy Lang_yelu_cmake AST and the Yelu_cmake_legacy_bridge are not called from any step binary. They remain callable only as the reference side of the byte oracle.
  • One pretty-printer. All cmake text goes through Lang_cmake_pp.pp — ~1.4k lines of well-tested formatting that emits valid cmake syntax for every cmake AST node. The typed IR collapses into the cmake AST via four short erasure helpers (arg quoting, target/name positions, cond tokenization, let substitution).

Theory fragments

Each cmake command family lives in its own pair of fragment files. A theory module defines a value-oriented set of constructors plus a per-theory eval_case; the matched yelu_cmake fragment defines the cmake-shaped equivalents (often with output-variable side effects).

Real means evaluation is meaningful at compile time (the theory carries its own semantics). Mixed means real for common ops, emit-faithful for the long tail. Compat means evaluation is placeholder — cmake's runtime owns the semantics, and yelu just emits faithfully.

Verification stack

Every cmake-text-producing path is verified against the legacy reference at multiple levels:

Byte-equality oracle

For every test program built as legacy AST, run both legacy_compile → pp and bridge → emit_ast → pp; assert byte-identical text. Catches any divergence between the legacy and new emit paths at the character level.

Status: 194/194 programs covered, 0 uncovered.

Pair-wise parser oracle

For every covered source program, run both parser paths (legacy parse → bridge → emit vs. new parse → emit) and assert byte-identical text. Catches parser-level divergence.

Status: 125 pair-wise cases across all 12 cmake command families.

cmake-only structural check

Compile each cmake-only step file to text; structurally compare against the reference CMakeLists from the cmake source tree. Catches semantic-equivalence drift even when the text differs in whitespace.

Status: 12/12 step pairs match.

runcmake-yelu (live cmake)

Run each yelu-generated cmake script through a real cmake instance; capture and diff stdout against running the reference script. End-to-end behavioral equivalence.

Status: 50/50 pairs byte-identical stdout.

From legacy to new

The current shape is the result of a phased retirement. The codebase started with a single legacy Lang_yelu_* stack (parser + AST + compile + 15 fragments + 14 typecheck modules) plus a parallel harness exploring theory composition. Production generation now runs through the harness; legacy is retained as the byte-equality reference and as the source of truth during the migration audit. Highlights of the retirement, in order:

  • Phase 1 — emit through cmake AST. Production text generation moved from the legacy direct compile to a path going through the typed Lang_cmake.exp AST and shared pretty-printer.
  • Phase 2a — parser directly to IR. A new Angstrom-based parser (Yelu_parse) reads the same concrete syntax and produces the typed IR directly, without going through the legacy AST.
  • Items A–D — gap closure + structural moves. Direct-parser gap list closed (try_compile, genex round-trip, kwarg-lists); binary callers repointed; the legacy parser/lexer relocated to yelu_legacy/; the harness directory renamed from yelu_tiny/ to yelu/.
  • E-utils — bridge off the binary path. A mirror constructor module (Yelu_cmake_utils) lets step files build typed IR directly; no production binary now calls the legacy bridge.
  • G — language-name honesty + legacy isolation. The two-language vocabulary (yelu_cmake / yelu_cmake_normal) anchored in every file/module name. Bridge moved to yelu_legacy/. The new directory has zero code-level imports of legacy modules.

Item F (parser dispatchers route through the ctor module) landed in late 2026-05; the parser now shares one source of truth with step files for how cmake command shapes become IR. Final E (module-level bridge deletion) remains open and not urgent, gated on shifting the byte oracle and pair-wise oracle from bridge-fed to source-fed shape.

What's next

With the production substrate stable, the design queue opens up:

Y17 — typing pass

A fresh typing model that uses the two-language form semantically: namespace separation, mutability/identity rules per theory, and the to_normal/from_normal pair as a place to push richer invariants. Unblocked now that retirement is done.

General vs cmake-specific theories

Several theories under yelu_cmake_normal_* are general-purpose (bool, int, string, list, store), not cmake-specific. Separating them into a shared core makes future yelu_shell / yelu_c packs cleanly reusable.

Split the shared expr

Today both languages extend the same Yelu_cmake.expr type. A clean separation gives each language its own expr, with truly shared core nodes (EVar, ESeq, ELet, …) staying in a small shared module.

Bar #3 — real-world cmake

Rewrite z3 / llvm / torch builds in yelu_cmake; prove structural equivalence with the original CMakeLists. The manifesto-level "does this scale" test — not started.
