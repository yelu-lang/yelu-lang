cmake Pain Points

Design decisions that make cmake hostile to static analysis, LLM synthesis, and human reasoning — and what yelu does about each one

These are not bugs. cmake is a remarkably capable tool that evolved organically over 20+ years. The goal is to identify the properties that make it hard to work with, and use those as design constraints for yelu.

1. Variable Names and Values Are the Same Type

The cmake problem

A variable name and a variable value are both plain strings. The distinction is purely positional — determined by where in a command the argument appears, not by any syntactic marker on the argument itself. 

set(myvar hello)         # "myvar" is a variable name (write target)
set(other ${myvar})      # "${myvar}" is a value (read expansion)
list(APPEND mylist ${x}) # "mylist" is an identifier; "${x}" is a value
foreach(i IN ZIP_LISTS a b) # "a", "b" are variable names ready by cmake

A reader (human or LLM) must know each command's argument schema to distinguish identifiers from values. Mistakes are silent: passing a value where a name is expected does not error — cmake just uses the string as-is.

What yelu does implemented

Yelu introduces a distinct type for variable identifiers. All command arguments that are variable identifiers take yelu_cvar; all arguments that are values take yarg. Passing a value where an identifier is expected is a compile-time type error. 

# yelu concrete syntax — names and values are syntactically distinct
( set 'CMAKE_CXX_STANDARD' "11";       # 'quoted' = variable name
  cache BUILD_SHARED_LIBS := ON;   # bare ident = cache variable name
  string_length 'hello' ~out:LEN   # ~out:VAR = output variable name (typed)
)

2. Implicit List Splitting on Semicolons

The cmake problem

cmake's fundamental data type is a string. Lists are strings where elements are separated by semicolons. Forgetting to quote a variable reference when the variable might contain semicolons causes silent argument splitting. 

set(myvar "a;b;c")
message(STATUS ${myvar})    # prints three separate args: "a" "b" "c"
message(STATUS "${myvar}")  # prints the single string "a;b;c"

This is cmake's most notorious footgun. The rule "always quote variable references" is widely repeated but frequently forgotten, and the failures are silent.

What yelu does done

Yelu strings containing whitespace or special characters are automatically emitted as quoted args by the compiler, preventing the most common splitting issue.

cmake

set(FLAGS "-Wall;-Wextra")
target_compile_options(tgt PRIVATE ${FLAGS})  # splits into two args ✓

yelu

# yelu: explicit lists, no semicolon encoding
( FLAGS := "-Wall", "-Wextra";
  compile_opts Target tgt ~private:[FLAGS]
)

3. Output Variables Are Named by the Caller

The cmake problem

cmake commands that produce output require the caller to supply the name of the variable to write into. Every call site carries an identifier that is purely a plumbing detail, not part of the computation. 

string(LENGTH "${mystr}" len_var)   # "len_var" is caller-chosen plumbing
math(EXPR result "${a} + ${b}")     # "result" is caller-chosen plumbing

LLMs generating cmake must track variable names across steps. Humans must invent names for intermediate results. The computation and the plumbing are interleaved.

What yelu addresses future

The let binding separates computation from plumbing: a yelu program binds intermediate results to compile-time names without those names leaking into the cmake output. Full expression composition (where commands return values that can be nested directly) is a future language design goal. 

# Desired future: commands return values, no plumbing names
( let len = string_length 'hello' in
  message "length: ${len}"   # len is a yelu binding, not a cmake variable
)

4. if() Boolean Semantics Require Policy CMP0012

The cmake problem

Without cmake_policy(SET CMP0012 NEW), the strings ON, YES, TRUE, 1 are not treated as boolean true in if(). They evaluate as false because cmake's old behavior treats unrecognized strings as variable names, and those variables are undefined (empty = false). 

set(eq ON)
if(${eq})            # evaluates FALSE without CMP0012 NEW!
if(${eq} STREQUAL "ON")  # works correctly regardless of policy

This surprises everyone the first time. LLMs trained on cmake snippets that assume modern policy behavior generate subtly broken code in older contexts.

What yelu does implemented

Yelu never generates bare if(${var}) for boolean-valued cmake variables. For cmake commands that return ON/OFF, yelu emits an explicit string comparison that works under any policy. 

# yelu: explicit comparison, policy-safe
( if str_eq ${result} 'ON' then
    ( message 'found' )
)

5. ERROR_VARIABLE Convention: NOTFOUND Means Success

The cmake problem

cmake commands that accept ERROR_VARIABLE set the variable to an error message on failure. On success, they set it to NOTFOUND — not to empty string. A check for "no error" must compare against NOTFOUND, not "". 

string(JSON result ERROR_VARIABLE err GET "${json}" key)
if(NOT err STREQUAL "NOTFOUND")   # correct success check
  message(FATAL_ERROR "error: ${err}")
endif()

Most developers expect "" to mean success. The cmake docs do not prominently document this behavior.

What yelu plans future

Yelu could wrap ERROR_VARIABLE commands with a result type (success/failure), hiding the NOTFOUND/error-message distinction entirely from callers.

6. string(JSON SET ...) Value Must Be a JSON Literal

The cmake problem

string(JSON ... SET json path value) requires value to be a valid JSON literal — a number, a JSON-quoted string, a boolean, or null. Passing a plain cmake string fails silently. 

string(JSON r SET [=[{"x":1}]=] y hello)       # fails — not a JSON literal
string(JSON r SET [=[{"x":1}]=] y [=["hello"]=]) # works — JSON string literal
string(JSON r SET [=[{"x":1}]=] y 42)           # works — JSON number

What yelu plans future

A typed yelu_json_value type (distinct from yarg) for the value argument would prevent passing a plain string. Currently the API accepts yarg and relies on the caller to pass an appropriate JSON literal.

7. Unnamed Named-Entity Namespaces

The cmake problem

cmake has at least nine independent named-entity namespaces, yet the language provides no syntactic marker to indicate which namespace an identifier belongs to:

Namespacecmake syntaxWhat the name denotes
Variableset(FOO val), ${FOO}a mutable variable slot
Targetadd_library(mylib ...)a build target object
Cacheset(FOO val CACHE STRING "")a persistent cache entry
Env$ENV{PATH}an environment variable
Command/Macrocmake_language(CALL myproc)a callable procedure
Moduleinclude(FetchContent)a loadable cmake module
Testadd_test(NAME mytest ...)a registered test case
Export setinstall(TARGETS ... EXPORT MyTargets)a named install manifest group
Propertyget_property(val TARGET t PROPERTY ...)a target/source attribute key

Namespace collisions are silent. A Variable and a Target can share a name — set(foo val) and add_library(foo ...) coexist — and cmake silently routes each reference to its namespace based on the calling command's argument schema.

Variable/Cache collision — the most dangerous case

The Variable and Cache namespaces share the same write command (set()), can hold different values under the same name, and have different read semantics depending on access method: 

set(VAR "normal")                    # writes to Variable namespace
set(VAR "cached" CACHE STRING "")    # writes to Cache namespace (same name)

On first configure, set(...CACHE...) is a dual-write: it sets both the cache entry and the normal variable. On re-configure, the same command becomes a silent no-op for both namespaces.

Scenario${VAR} readsWhy
First configure"cached"Cache set also wrote normal
Re-configure"cached" (from previous run)Cache entry sticky, normal untouched
unset(VAR) then cache set"cached"Cache still exists, normal re-set
unset(VAR) after cache set"cached"unset only removes normal; cache persists

What yelu does implemented

Yelu records the namespace explicitly in the AST. A name like { ns = Ns_var; name = "VAR" } is distinct from { ns = Ns_cache; name = "VAR" }. The wellform pass checks that all references resolve to declarations within their namespace.

8. Computation and Storage Are Fused

The cmake problem

cmake has no return values. Every command that produces a result must write it into a named variable slot. This fuses two concerns that are separate in most languages: "what is the result?" and "where should it be stored?" 

string(LENGTH "${mystr}" len_var)       # computation + storage in one call
math(EXPR result "${a} + ${b}")         # same pattern, different command
find_package(Boost REQUIRED)              # implicitly writes Boost_FOUND, Boost_INCLUDE_DIRS, ...

This is cmake's fundamental design constraint — no return values — but it means:

  • Every intermediate value needs a named variable slot
  • LLMs must generate unique, non-colliding names for every step
  • The computation graph is implicit in variable names, not explicit in the program structure

What yelu addresses partial

Yelu's let-binding provides a compile-time name that does not leak into cmake output. The wellform pass tracks every variable definition and use, so typos are caught before cmake runs. 

# yelu: computation and storage are still fused in generated cmake,
# but the yelu-level name (len) is checked and scoped
( let len = string_length 'hello' ~out:LEN in
  message "length: ${LEN}"
)
