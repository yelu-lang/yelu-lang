Translation Equivalence

How yelu verifies that its output means the same thing as the input

Overview

The yelu compiler translates typed yelu programs into plain cmake text. Translation is correct when the generated cmake behaves identically to a reference implementation. Correctness is verified at multiple levels of increasing strength — from text comparison through build artifacts to codemodel inspection. Every level acts as a regression net: a change that passes all levels is unlikely to have altered semantics.

Each level subsumes all levels below it: a build test also passes configure, script, and text.

How Translation Equivalence Works

Level 1 — text equivalence

The simplest level: compile a yelu program, format the output with gersemi, compare to the reference cmake. This is the first line of defense — any drift in the emitted cmake text is caught immediately. Both the cmake pretty-printer and the yelu compiler have dedicated Alcotest suites.

Level 2 — script equivalence (script-pair)

Structural equivalence (same text) is necessary but not sufficient. Two cmake programs can be textually different yet semantically identical (different argument order, different quoting). Script-pair tests run both the reference cmake and the yelu-generated cmake through cmake -P and compare stdout: 

# Reference cmake (upstream RunCMake test)
cmake_path(SET path "/a/b")
cmake_path(APPEND path "c")
message("${path}")

# yelu-generated cmake — may differ textually but must produce identical stdout
cmake_path(SET path "/a/b")
cmake_path(APPEND path "c")
message("${path}")

Both must exit 0 and produce /a/b/c. When a yelu change silently alters semantics (PP quoting, arg ordering), the reference output is ground truth and the test catches the drift immediately.

Level 3 — configure and build

Some cmake constructs are only meaningful in configure mode (not cmake -P). The cmake-check suites run the full configure pipeline and verify exit codes, cache variable bindings, and generated buildsystem structure. 

# yelu: generate CMakeLists.txt from yelu program
# cmake: configure -S tmpdir -B build
# Compare: exit code, cache vars (CMAKE_CXX_STANDARD, etc.)

Build-level tests go further: they run cmake --build on both the reference and yelu-generated buildsystems, then compare artifact names and counts. The test harness uses fate-sharing: all four outcomes (ref configure, ref build, yelu configure, yelu build) are checked independently, so a test that fails in both ref and yelu is identified as an environmental issue rather than a yelu regression.

Level 4 — codemodel inspection (file-api)

The strongest current level queries cmake's File API (codemodel-v2) after configure. This exposes the full binding environment: every target's compile flags, include directories, link libraries, and dependencies. The yelu and reference codemodels must produce identical JSON (modulo ordering).

Symbolic Equivalence research

All current levels test equivalence at one concrete input configuration. With n boolean option variables, there are 2n configurations; no test-based level can prove equivalence for all of them. Symbolic methods are the only path to closing this gap.

The research gap

cmake's configure-time language is a restricted imperative language: straight-line code + boolean conditionals, string-typed mutable state, 6 independent namespaces, finite iteration, and opaque side-effectful commands. Two approaches are under investigation:

ApproachNatural fitChallenge
E-graphs (egg/egglog) Equality saturation could discover that reordered set() calls commute when variables don't alias Statefulness. cmake is order-sensitive; e-graphs excel over functional expressions. Encoding state transformers as terms is non-trivial.
SMT / Z3 Boolean skeleton + string theory covers if() conditions and variable read/write cmake's string semantics (list splitting, genex expansion, implicit namespace resolution) don't map cleanly to SMT string theories. Encoding the full cmake reduction semantics is substantial.

Why this matters

The equivalence oracle is yelu's key verification mechanism. For the thesis to hold, we need to show that yelu's output is provably equivalent to reference cmake — not just equivalent on a finite test suite. Symbolic methods are the path to that guarantee, and the design of yelu's restricted imperative core (no unbounded loops, explicit namespaces, regular syntax) directly reduces the complexity of that encoding.
